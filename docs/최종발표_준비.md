## 2. PPT 슬라이드 텍스트 (3분, 6장)

각 슬라이드: 위쪽은 화면에 넣을 글, 아래 "말할 내용"은 발표 대본.

### 슬라이드 1 — 제목

- Pedal Point
- 달린 만큼 쌓이는 탄소 마일리지 공공자전거 서비스
- 데이터베이스 최종발표 · 5조
- 윤하원 · 허영훈

말할 내용 (15초)
> 5조 Pedal Point 최종발표입니다. 중간발표에서 계획했던 탄소 마일리지 공공자전거 서비스를 실제로 구현했고, 오늘은 완성된 결과를 보여드리겠습니다.

### 슬라이드 2 — 프로젝트 목적

- 제목: 왜 만들었나
- 공공자전거 이동 = 승용차 이동을 대신한 탄소 절감
- 기존 서비스: 환승·재배치 마일리지는 있지만, 환경 기여를 직접 보상하지는 않음
- Pedal Point: 이동거리 → 탄소 절감량 → 마일리지 → 다음 결제 할인 을 한 시스템 안에서 연결
- 핵심 메시지: "환경을 생각한 이동이 곧 혜택이 된다"

말할 내용 (25초)
> 자전거로 이동하면 그만큼 승용차 탄소가 줄어듭니다. 그런데 기존 공유 자전거 서비스는 이 기여를 이용자에게 돌려주지 않습니다. 저희는 이동거리를 탄소 절감량과 마일리지로 바꾸고, 그 마일리지로 다음 요금을 할인받는 흐름을 하나의 데이터베이스 안에서 연결했습니다.

### 슬라이드 3 — 서비스 흐름

- 제목: 이용 흐름
- (도식) 대여소 선택 → 대여 → 이동 → 반납 → 결제(마일리지 할인) → 마일리지 적립
- 요금: 기본 60분 1,000원, 30분 초과마다 500원
- 적립: 1km당 100P (1P = 1원)
- 탄소: 1km당 210g 절감 → 소나무 흡수량 등 생활 속 수치로 표시

말할 내용 (20초)
> 이용자는 지도에서 대여소를 골라 빌리고, 반납할 때 이동거리에 따라 요금이 계산됩니다. 보유 마일리지로 할인받고, 이번 이동거리만큼 새 마일리지가 쌓입니다. 줄인 탄소는 소나무 몇 그루 분량처럼 체감할 수 있는 수치로 보여줍니다.

### 슬라이드 4 — 주요 기능

- 제목: 구현 기능
- 이용자
  - 회원가입·로그인 (비밀번호 bcrypt 암호화, 실시간 입력 검사)
  - 지도 기반 대여소 검색·대여 (대여 가능 대수 표시)
  - 반납·결제·마일리지 할인, 결제 대기 건 결제
  - 홈 대시보드: 탄소 절감·나의 숲 단계·이번 달 목표·순위
  - 마이페이지: 대여·결제·마일리지 내역, 정보 수정, 탈퇴
- 관리자
  - 대여소·자전거 등록, 정비 상태 변경 (지도에서 위치 지정)
  - 대여·결제·마일리지 내역 조회 (기간·회원·대여소 필터)
  - 회원 상태 관리, 탄소·마일리지 통계
- 공통: PC/모바일 화면 자동 전환, 라이트/다크 테마

말할 내용 (25초)
> 이용자 화면은 회원가입부터 대여, 반납, 결제, 내역 조회까지 전부 동작합니다. 관리자는 대여소와 자전거를 관리하고, 내역을 조건별로 조회하며 회원 상태와 통계를 봅니다. 자세한 동작은 잠시 뒤 시연으로 보여드리겠습니다.

### 슬라이드 5 — 데이터베이스 구조 (ERD)

- 제목: 데이터베이스 구조
- (그림) docs/ERD.png
- 테이블 7개 · 외래키 8개 · CHECK 제약 9개
  - station 대여소 / adminstaff 관리자 / bicycle 자전거 / user 이용자
  - rental 대여 / payment 결제 / mileage 마일리지 적립
- 관계 요약
  - 이용자·자전거·대여소가 rental(대여)로 모인다 (대여소는 출발·반납 두 번 연결)
  - 대여 1건 : 결제 최대 1건 : 적립 최대 1건 (UNIQUE로 보장)
  - 관리자는 담당 대여소 1곳, 자전거는 현재 있는 대여소를 가리킴

말할 내용 (45초)
> 테이블은 7개입니다. 중심은 대여 테이블로, 누가 어떤 자전거를 어느 대여소에서 빌려 어디에 반납했는지와 이동거리를 기록합니다. 대여소는 출발과 반납 두 개의 외래키로 연결됩니다. 결제와 마일리지 적립은 대여 한 건에 각각 최대 한 건이라 대여 번호에 UNIQUE를 걸었습니다. 이용자 테이블의 보유 마일리지는 매번 합계를 계산하지 않도록 따로 저장하고, 결제할 때 같은 트랜잭션에서 함께 갱신합니다.

### 슬라이드 6 — 무결성 설계

- 제목: 데이터를 지키는 방법
- 제약조건 (DB가 직접 막음)
  - 반납 시각·반납 대여소·이동거리는 셋 다 비었거나 셋 다 채워짐 (CHECK)
  - 최종 결제액 = 이용금액 − 할인액, 할인액 ≤ 이용금액 (CHECK)
  - 마일리지·거치대 수·이동거리 음수 불가 (CHECK)
  - 아이디·연락처 중복 불가 (UNIQUE)
  - 이력이 있는 회원·자전거·대여소는 삭제 불가 (ON DELETE RESTRICT) → 회원은 상태(정상·정지·탈퇴)만 변경
- 트랜잭션 (프로그램이 막음)
  - 대여, 반납+결제+적립을 각각 한 트랜잭션으로 → 중간에 실패하면 전부 취소
  - SELECT … FOR UPDATE로 행을 잠가 같은 자전거 동시 대여 방지

말할 내용 (40초)
> 데이터가 어긋나지 않도록 두 단계로 지켰습니다. 먼저 DB 제약조건으로, 반납 정보가 반만 채워지거나 결제 금액 계산이 맞지 않는 데이터는 DB가 저장을 거부합니다. 이력이 남은 회원은 삭제하지 않고 상태만 바꿉니다. 다음으로 대여와 반납·결제는 하나의 트랜잭션으로 묶고 관련 행을 잠가서, 두 사람이 같은 자전거를 동시에 빌리는 상황도 막았습니다. 그럼 시연으로 넘어가겠습니다.

> 목차 슬라이드는 3분에 넣기 빠듯해서 뺐습니다. 넣고 싶으면 슬라이드 1과 2 사이에 "목적·기능 / 데이터베이스 구조 / 시연" 세 줄로만.
> "감사합니다" 슬라이드는 Q&A 때 띄워 두기용으로 마지막에 하나 두면 좋습니다.

## 4. Q&A 대비

### 4-1. 데이터베이스 구조의 취약점

인정할 건 인정하고 "알고 있고, 이렇게 보완할 수 있다"로 답한다.

**Q. 보유 마일리지(user_mileage)를 따로 저장하면 내역 합계와 어긋날 수 있지 않나?**
> 맞습니다, 반정규화라서 이론상 어긋날 수 있습니다. 조회할 때마다 적립·사용 내역을 합산하지 않으려고 둔 값이고, 대신 결제·적립과 같은 트랜잭션에서 이용자 행을 잠근 뒤 함께 갱신해서 프로그램을 통해서는 어긋나지 않게 했습니다. 더 확실히 하려면 트리거로 갱신하거나, 주기적으로 내역 합계와 비교하는 검증 쿼리를 둘 수 있습니다.

**Q. 마일리지 사용 내역 테이블이 없는데?**
> mileage 테이블은 적립만 기록하고, 사용은 payment의 할인액(payment_discount)으로 기록합니다. 마일리지는 결제할 때만 쓰이므로 결제 행이 곧 사용 내역입니다. 다만 소멸이나 관리자 지급처럼 결제와 무관한 변동이 생기면 적립·사용 구분 컬럼을 둔 거래 내역 테이블로 바꾸는 게 맞습니다.

**Q. 1인 1대 대여, 빈 거치대 확인은 DB 제약으로 막혀 있나?**
> 아닙니다. 여러 행을 세어야 하는 규칙이라 CHECK로는 표현이 안 돼서, 트랜잭션 안에서 SELECT … FOR UPDATE로 잠근 뒤 프로그램에서 확인합니다. 따라서 DB에 직접 SQL을 넣으면 우회될 수 있습니다. 보완책은 트리거, 또는 1인 1대의 경우 "대여 중일 때만 값이 생기는 생성 컬럼 + UNIQUE 인덱스"입니다.

**Q. 이동거리를 이용자가 직접 입력하면 조작할 수 있지 않나?**
> 맞습니다. 과제 범위에서는 GPS 연동이 없어 입력으로 대신했고 0 ~ 99.99km로 범위만 제한했습니다. 실제 서비스라면 자전거 단말기의 GPS 기록이나 대여소 간 거리로 계산해야 합니다. DB 구조는 거리 값을 어디서 받든 그대로 쓸 수 있습니다.

**Q. 요금 규칙이 DB에 없는데 요금이 바뀌면?**
> 요금·적립 기준은 프로그램(rules.py)에 있고, DB에는 계산된 결과 금액만 저장합니다. 그래서 과거 결제 금액은 규칙이 바뀌어도 그대로 남습니다. 요금 정책 이력까지 관리하려면 요금제 테이블을 만들고 결제에 요금제 번호를 연결하면 됩니다.

**Q. 대여소 좌표(위도·경도)가 없는데 지도는 어떻게?**
> 확정된 DB 구조에는 좌표 컬럼이 없어서 좌표를 별도 JSON 파일에 대여소 번호로 저장했습니다. 구조를 다시 설계한다면 station에 위도·경도 컬럼을 넣는 게 맞고, 그러면 거리 기준 대여소 검색도 SQL로 할 수 있습니다.

**Q. 대여 중인 자전거의 위치(bicycle_station_id)가 NULL인데 문제없나?**
> 대여 중일 때는 어느 대여소에도 없으므로 NULL로 두고 상태를 RENTED로 표시합니다. 다만 대여소를 지워도 ON DELETE SET NULL로 NULL이 되기 때문에 NULL만으로는 구분이 안 되고 상태 컬럼을 함께 봐야 합니다. 실제로는 대여소를 지우지 않고 운영 중지(INACTIVE)로 바꾸게 했습니다.

**Q. 결제 대기 상태 컬럼이 따로 없는데?**
> "반납은 됐는데 결제 행이 없음"으로 판단합니다. 상태를 중복 저장하지 않아 어긋날 일은 없지만, 매번 LEFT JOIN이 필요합니다. 데이터가 많아지면 rental_end_time 등에 인덱스를 추가하는 게 좋습니다.

**Q. 관리자 한 명이 대여소 여러 곳을 맡을 수 없지 않나?**
> 맞습니다. 현재는 관리자 1명당 담당 대여소 1곳(staff_station_id)입니다. 여러 곳을 맡으려면 관리자-대여소 연결 테이블로 다대다 관계를 만들어야 합니다.

**Q. 탈퇴 회원의 연락처는?**
> 행을 지우지 않으므로 연락처 UNIQUE 때문에 같은 번호로 다시 가입할 수 없습니다. 개인정보 측면에서도 탈퇴 시 연락처를 비식별 값으로 바꾸는 처리가 필요합니다. 현재 구현의 한계입니다.

**Q. 중간발표에 있던 고장 신고 기능은?**
> 팀에서 DB 구조를 확정하면서 신고 테이블을 빼고, 관리자가 자전거 상태를 '정비중'으로 바꾸는 기능으로 대신했습니다. 신고를 넣으려면 신고자·자전거·내용·처리 상태를 가진 report 테이블을 추가하면 됩니다.

**Q. 외래키 옵션이 왜 다 다른가? (반납 대여소만 ON UPDATE RESTRICT)**
> 대부분 ON UPDATE CASCADE, ON DELETE RESTRICT입니다. 이력이 남은 행은 삭제 못 하게 하고, 소속(관리자·자전거의 대여소)은 대여소가 사라지면 SET NULL로 했습니다. 반납 대여소 FK만 ON UPDATE RESTRICT인데, 실제로 기본키를 바꾸는 일은 없어서 동작에 영향은 없지만 통일하는 게 깔끔합니다.

**Q. 정규화는 몇 정규형?**
> 반복 그룹이 없고, 모든 테이블이 단일 대리키(AUTO_INCREMENT)라 부분 종속이 없으며, 이행 종속도 두지 않아 3정규형입니다. 예외는 의도적으로 둔 보유 마일리지 하나입니다.

### 4-2. 프로그램 구동 시 발생하는 상황

**Q. 두 사람이 같은 자전거를 동시에 누르면?**
> 대여 트랜잭션이 자전거 행을 SELECT … FOR UPDATE로 잠급니다. 먼저 잠근 사람이 대여하고, 뒤 사람은 잠금이 풀린 뒤 상태가 이미 RENTED라 "이미 대여되었거나 대여할 수 없는 자전거입니다"가 뜹니다.

**Q. 반납하다가 결제 단계에서 오류가 나면?**
> 반납, 결제, 적립, 보유 마일리지 갱신이 하나의 트랜잭션이라 중간에 실패하면 전부 롤백됩니다. 반납만 되고 결제가 빠지는 일은 없습니다. 대신 반납만 해 두고 결제를 나중에 하는 '결제 대기' 흐름은 따로 있습니다.

**Q. 이미 대여 중인데 또 빌리려 하면? / 정지 회원이면? / 탈퇴 회원이면?**
> 대여 중이면 대여 화면 대신 반납 화면이 나오고, 강제로 요청해도 "이미 대여 중인 자전거가 있습니다"로 막힙니다. 정지 회원은 로그인은 되지만 대여할 수 없고, 탈퇴 회원은 로그인 자체가 안 됩니다.

**Q. 반납 대여소가 꽉 찼거나 운영 중지면?**
> 반납 대여소를 고를 때 빈 거치대 수를 보여주고, 결제 직전에도 대여소 행을 잠그고 다시 세어서 "빈 거치대가 없습니다. 다른 대여소를 선택하세요"로 막습니다. 운영 중지 대여소도 거부합니다.

**Q. 마일리지를 보유량보다 많이 쓰려 하면?**
> 할인 한도는 이용금액과 보유 마일리지 중 작은 값입니다. 화면에서 한도를 넘게 입력할 수 없고, 서버에서도 다시 확인합니다. DB에도 할인액 ≤ 이용금액, 마일리지 ≥ 0 CHECK가 있어 3중으로 막힙니다.

**Q. 방금 적립된 포인트를 바로 쓸 수 있나?**
> 아닙니다. 할인 한도를 적립 전 잔액으로 계산하므로 이번 대여로 쌓인 포인트는 다음 결제부터 쓸 수 있습니다.

**Q. 대여 중이거나 결제 안 한 회원이 탈퇴하면?**
> 탈퇴가 거부되고 "반납 후" 또는 "결제 후 다시 시도하세요"가 뜹니다. 관리자도 대여 중인 회원은 정지·탈퇴로 바꿀 수 없습니다.

**Q. 관리자가 회원 여러 명을 고치다 하나가 틀리면?**
> 회원 표의 변경을 한 트랜잭션으로 저장해서, 하나라도 규칙에 어긋나면 전부 취소되고 어느 회원에서 틀렸는지 알려줍니다.

**Q. 중복 아이디·연락처로 가입하면?**
> DB의 UNIQUE 제약이 막고, 프로그램은 MySQL 오류 번호 1062를 받아 "이미 사용 중인 아이디 또는 연락처입니다"로 바꿔 보여줍니다.

**Q. DB가 꺼져 있거나 예상 못 한 DB 오류가 나면?**
> 원래 오류는 서버 콘솔 로그에 남기고, 화면에는 "처리 중 오류가 발생했습니다. 다시 시도해 주세요."만 보여줍니다. 내부 오류 내용을 이용자에게 노출하지 않기 위해서입니다.

**Q. 비밀번호는 어떻게 저장하나? SQL 인젝션은?**
> bcrypt로 해시해서 저장하므로 DB를 봐도 원래 비밀번호를 알 수 없습니다. 모든 SQL은 %s 파라미터 바인딩으로 실행해서 입력값이 SQL 문으로 해석되지 않습니다.

**Q. 요금은 어떻게 계산되나? 예를 들어 95분이면?**
> 기본 60분 1,000원, 넘는 시간은 30분 단위로 올림해 500원씩입니다. 95분이면 35분 초과 → 2단위 → 2,000원입니다.

**Q. 인터넷이 끊기면?**
> DB와 서버는 PC 한 대에서 돌아서 대여·반납은 동작하지만, 지도 타일은 OpenStreetMap에서 받아오므로 지도 배경이 안 보입니다. 이름·주소 검색으로 대여소를 고를 수 있습니다.

**Q. 모바일에서도 되나?**
> 같은 주소로 접속하면 창 비율을 보고 모바일 전용 화면(하단 탭)으로 바뀝니다. 같은 Wi-Fi의 휴대폰에서 접속할 수 있고, 관리자는 PC 화면만 지원합니다.
